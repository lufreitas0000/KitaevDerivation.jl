# Adversarial Verification

## Purpose

This skill exists to detect a specific failure mode:

> The software passes its tests while violating the mathematical or physical specification.

A green test suite is evidence that executed assertions passed.
It is NOT, by itself, evidence that the implementation is scientifically correct.

The verifier must therefore actively search for implementations that can produce
green tests while being mathematically wrong.

---

# Core Principle

The verification target is:

    mathematical specification
            ↓
    independent mathematical oracle
            ↓
    executable invariant
            ↓
    implementation
            ↓
    PASS / FAIL

The following structure is forbidden:

    implementation
            ↓
    expected result derived from implementation
            ↓
    test
            ↓
    PASS

The second structure is implementation/test coupling and is not an independent
verification argument.

---

# Threat Model

Assume the implementation may contain:

- hardcoded outputs;
- mock implementations;
- surrogate expressions;
- ignored physical parameters;
- wrong signs;
- missing numerical factors;
- incorrect normalization;
- incorrect fermionic ordering;
- incorrect projector definitions;
- incorrect energy denominators;
- missing terms;
- over-aggressive symbolic simplification;
- incorrect basis transformations;
- special-case implementations that only work at one parameter point;
- unconditional assertions;
- `@test true`;
- tests copied from implementation expressions;
- tests whose expected values are generated by the implementation itself;
- tests that only check types or execution;
- tests that exercise code without checking mathematical meaning.

The verifier must actively attempt to expose these failure modes.

---

# Declared Provenance

Every nontrivial scientific assertion must have declared provenance.

Declared provenance means that the test documents where its expected mathematical
result came from independently of the implementation being tested.

For example:

    Physical statement:
        E[L=1] = U - 3 J_H

    Provenance:
        Kanamori analytical derivation
        → independently stated equation
        → expected symbolic expression
        → executable test

The expected result must NOT be obtained by:

    implementation
        → inspect implementation output
        → copy output into test
        → assert equality

A valid provenance record should identify:

1. The mathematical or physical statement being tested.
2. The independent source of that statement.
3. The derivation or reasoning connecting the source to the expected result.
4. The executable invariant used by the test.
5. Why the invariant discriminates the correct implementation from plausible
   incorrect implementations.

For repository physics, acceptable provenance can include:

- an explicitly documented analytical derivation;
- a paper/equation specified by the project;
- a manually derived symbolic identity;
- an independently constructed reference expression;
- an independently constructed finite-dimensional numerical calculation;
- a Lean theorem or formally verified algebraic identity.

The implementation under test must not be the sole source of its own oracle.

---

# Fake-Green Detection

A test suite is considered vulnerable to a fake green pass when an obviously
incorrect mutation can pass the existing tests.

The verifier must therefore perform adversarial mutations whenever practical.

Examples:

    correct:
        U - 3 J_H

    mutations:
        U - 2 J_H
        U + 3 J_H
        2(U - 3 J_H)
        U - 3 J_H / 2
        U

Every scientifically meaningful mutation should be rejected by at least one
independent invariant.

Other mutations include:

- flip a sign;
- remove a term;
- multiply by 2;
- divide by 2;
- replace an operator with zero;
- replace an operator with identity;
- return a constant;
- ignore an input parameter;
- use the wrong basis;
- swap two fermionic operators;
- replace a projector by another projector;
- replace a symbolic expression by a hardcoded special-case result.

If a wrong mutation remains green, report:

    TEST SUITE INSUFFICIENT

Do not modify the mutation to make the test pass.

---

# Implementation/Test Coupling

Look for tests containing patterns such as:

    expected = function_under_test(...)
    @test function_under_test(...) == expected

or:

    expected = implementation_internal_expression

or:

    expected = expression_generated_by_same_algorithm

These are not independent tests.

Also flag tests that verify only:

- that a function returns something;
- that an expression has a particular type;
- that a computation does not throw;
- that a hardcoded value equals itself;
- `@test true`;
- unconditional assertions;
- values produced by the same helper that produced the implementation result.

---

# Placeholder and Vacuous Tests

The following are verification failures unless explicitly justified:

    @test true

    @test 1 == 1

    @test !isnothing(result)

    @test result !== nothing

when these assertions are used as substitutes for the mathematical contract.

Comments such as:

    TODO
    placeholder
    temporary
    until rules are populated
    CI placeholder
    mock
    surrogate

must be treated as evidence requiring investigation.

A placeholder test must never be counted as evidence that a scientific invariant
has been verified.

---

# Parameter-Sensitivity Verification

Every physically meaningful parameter must be audited.

For each parameter, determine:

1. Where does it enter the mathematical specification?
2. Where does it enter the implementation?
3. Where is its effect tested?
4. Can the parameter be changed without changing the relevant result?
5. If its effect is mathematically zero, is that zero independently justified?

Example:

    t' = next-nearest-neighbor hopping

If the implementation accepts `t'` but never uses it, this is a potential defect.

However, the verifier must NOT automatically assume that a zero contribution
is wrong.

Instead determine whether:

    t' contribution = 0

is an actual consequence of the stated approximation, order in perturbation
theory, geometry, or symmetry.

A parameter may be ignored computationally only when the mathematical reason
for doing so is explicitly established.

---

# Limiting-Case Verification

Test physically meaningful limits independently.

Examples:

    J_H = 0
    λ_SOC → 0
    t' = 0
    t' ≠ 0
    hopping = 0
    symmetry-related parameter choices

The expected behavior must come from the physical specification rather than
from observing what the implementation happens to produce.

For the Kitaev derivation, verify at minimum:

    J_H = 0  ⇒  J = K = 0

    λ_SOC → 0  ⇒  K = 0

    z-bond C2 symmetry  ⇒  J_xx = J_yy

---

# Algebraic Invariants

Verify mathematical identities rather than merely implementation outputs.

For fermionic algebra:

    {cα, cβ†} = δαβ

    {cα, cβ} = 0

Projectors must satisfy:

    P² = P

    Pi Pj = 0       for i ≠ j

    Σ Pi = I

Do not accept tests that merely inspect the internal representation of these
objects without verifying the algebraic identity.

---

# Physical Invariants

Use the project's declared physical oracles.

Important examples include:

    ΔE(jeff=3/2) - ΔE(jeff=1/2) = 3 λ / 2

    ΔE[L=0] = U + 2 J_H

    ΔE[L=1] = U - 3 J_H

    ΔE[L=2] = U - J_H

These are scientific contracts, not implementation details.

---

# Hardcoded-Result Detection

A function is suspicious when its output is independent of inputs that should
physically affect the result.

For example:

    function project_jeff_half(op, ...)
        return λ / 2 * P_half
    end

is suspicious if the result does not depend on `op`.

The verifier must ask:

    Does the mathematical operation being implemented actually act on `op`?

If not, the implementation is a mock/surrogate unless explicitly justified.

---

# Independence Requirement

The following roles must remain conceptually separate:

    implementation
    test generation
    scientific auditing
    formal verification

The same agent should not:

1. invent a mathematical specification;
2. implement that specification;
3. write the tests;
4. declare the implementation correct.

When possible, these steps should be independently performed or reviewed.

---

# Adversarial Questions

For every important function, ask:

1. What happens if I replace the implementation with a constant?
2. What happens if I remove one term?
3. What happens if I flip a sign?
4. What happens if I multiply the result by 2?
5. What happens if I ignore one input parameter?
6. What happens if I use the wrong basis?
7. What happens if I use the wrong fermionic ordering?
8. What happens if I return the expected result directly?
9. Would the current tests detect these mutations?
10. Is the expected result independently derived?

If the answer to question 9 is "no", the test suite is insufficient.

---

# Scientific Repair Boundary

This skill is for verification.

The verifier must not silently repair mathematical defects while auditing them.

When a defect is found:

    identify
        ↓
    reproduce
        ↓
    explain
        ↓
    identify missing invariant/oracle
        ↓
    report

Repair belongs to the appropriate implementation/test agent after the defect
has been independently characterized.

---

# Phase-Gate Requirement

A phase cannot be declared scientifically complete merely because:

    julia test/... passes

The phase gate requires:

1. executable tests pass;
2. mathematical invariants pass;
3. physical invariants pass;
4. no known placeholder tests remain;
5. no unexplained hardcoded scientific results remain;
6. important parameters have been audited;
7. at least one adversarial mutation campaign has been performed for
   critical results;
8. independent provenance exists for critical expected results;
9. Lean verification passes where a formal contract exists;
10. physics-auditor finds no unresolved critical violation.

---

# Failure Policy

Any of the following is a verification failure:

- a critical invariant is absent;
- a critical invariant is implemented as `@test true`;
- expected values are derived from the implementation;
- a plausible wrong mutation passes;
- a physical parameter is silently ignored without justification;
- a hardcoded scientific result replaces required algebra;
- a mock/surrogate is presented as a real implementation;
- a test was weakened to restore green CI;
- a mathematical convention was changed solely to satisfy tests.

Green CI must never override a scientific failure.

# Verification Report

The verifier must report findings using:

    Finding:
    Severity:
    Location:
    Scientific contract:
    Declared provenance:
    Current test:
    Why the test can pass incorrectly:
    Adversarial mutation:
    Expected mutation result:
    Actual mutation result:
    Required repair:
    Verification status:

Severity levels:

    CRITICAL
    HIGH
    MEDIUM
    LOW

A CRITICAL finding blocks the phase gate.

---

# Completion Criteria

The adversarial verification task is complete only when:

- critical invariants have declared provenance;
- critical tests are independently derived;
- placeholder/vacuous tests have been eliminated or explicitly justified;
- critical parameters have been audited;
- critical mutations are rejected;
- no known implementation/test circularity remains;
- unresolved scientific defects are explicitly reported;
- the verifier has not silently repaired the implementation.
